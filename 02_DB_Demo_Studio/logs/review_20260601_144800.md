## P1 — 强烈建议修复

### 1. `architecture.md` 的 LLM Provider 描述违反 DeepSeek-only 约束

- **文件和位置**：`02_DB_Demo_Studio/docs/architecture.md`，技术栈部分
- **严重程度**：P1
- **问题描述**：文档写的是 `LLM API（DeepSeek / GPT-4o / Azure OpenAI 可切换）`，但当前学习约束已经明确以后只能使用 DeepSeek API。这个表述会诱导后续实现多 Provider 抽象，增加不必要复杂度，也可能让后续代码接入 OpenAI/Azure 配置，违背项目约束。
- **建议修复方式**：
  - 改为：`DeepSeek API（OpenAI-compatible SDK）+ Agent 编排...`
  - 若未来需要私有化或备用模型，先写到 Phase 2/风险项，不进入 Phase 1 主实现。

### 2. Agent 规则允许 `explain_mysql 和/或 explain_postgres`，弱化双引擎要求

- **文件和位置**：`02_DB_Demo_Studio/docs/ai-workflow.md`，Demo Agent system prompt 规则
- **严重程度**：P1
- **问题描述**：需求文档 Q4 要求 MySQL + PostgreSQL 对齐真实执行计划语义；架构也把双引擎 EXPLAIN 作为 grounding 关键路径。但 Agent 规则写成“和/或”，会让 SQL 演示在没有明确降级说明时只调用一个引擎也被视为合格，后续实现和验收容易跑偏。
- **建议修复方式**：
  - 改为：SQL 类演示默认必须调用 `explain_mysql` 和 `explain_postgres`。
  - 若某一引擎失败，必须产生 `engineFallback` / `issues[]`，并在 DemoPackage 中标注降级原因。
  - Phase 1 如只完整实现 MySQL，应在 README 和验收标准中明确：PostgreSQL 是占位/部分对照，而不是“和/或”随机选择。
